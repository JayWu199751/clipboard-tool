- **暗色描边四边不等宽（2026-09-05）**：收敛后的真机复核抓到两个叠加的视觉缺陷。其一：`.desktop` 的 padding 沿用收敛前「上/左 0、右/下 1px」的不对称值，暗色描边压在窗口物理边缘的上/左两条边被透明窗口 per-pixel alpha 裁得不可见，只剩右/下可见——修为四边对称 `padding: 1px`。其二：修完仍不等宽，逐像素测量（Playwright 截图 + 复用托盘脚本的零依赖 PNG 解码器，沿边积分覆盖率）量出 150% 缩放下右缘 2.1、左缘 1.0 设备像素——根因是 Chromium 把 border 与 inset box-shadow 的绘制矩形逐边取整到整数设备像素，1 CSS px=1.5 设备像素时四边各落一或两个像素上，且调窄 CSS 宽度不改光栅。修为按 `resolution` 媒体查询把 `.desktop` padding 与 `.app-window` border-width（浅暗两主题）同归一成 1/dppx，盒边缘与描边宽度都恰为整数设备像素，取整无分数部分；暗色描边同时从 inset box-shadow 改为真 border（阴影矩形逐边独立取整更不可控）。100%/200% 整数 DPR 天然精确，200% 以上非整数缩放罕见未覆盖。测量基建沉淀为 `tests/window-ring-width.spec.js` 3 例（dpr 1/1.25/1.5，先隐藏卡片子元素——各子元素背景透明度不同会按边盖暗描边，`omitBackground: true` 防截图白垫把半透明边缘垫亮成假描边），修复前 dpr1.25 极差 0.54、1.5 极差 0.89，修复后分别 0.05 与 0.01。完整根因链与测量方法记入 [pitfalls 第 3 节](desktop-tool-pitfalls.md)。`styles.css` +31/-7、新增 spec 125 行；73 例（node 14 + cargo 59）、`test:browser` 3 → 6 例、`tsc --noEmit` 与 `cargo check --all-targets` 零报错零警告。分数缩放档位的实际观感仍需真机复核（见 README「待真机验证」）。

- **窗口框架覆盖层收敛为单一权威定义（2026-09-05）**：用户反馈「调 `.desktop` padding 和 `.app-window` 边框线宽不生效」。根因不在那两行，而在 `styles.css` 的沉淀方式：同一属性被 fix3/fix3b/fix4/fix5/fix6、Apple 覆盖层、Cathedral 层、Unified 层等 8 层历史补丁反复用 `!important` 重声明——`.desktop` 的 padding 声明了 8 次（0→0→0→0→2px→2px→8px→`0 1px 1px 0`）、`.app-window` 的 border 声明了 7 次，谁生效只取决于谁在文件里更靠后，改前面任何一层都是死代码。本次先逐层盘点两个选择器（连同 html/body/#root 尺寸链与 `.titlebar`/`.shortcut-bar` 圆角联动）的全部声明，按「418×823 视口下两条 `max-width` 媒体查询恒命中、同优先级 `!important` 后者胜」算出级联终值，然后把终值落成文件头部一节带契约注释的「窗口框架 — 单一权威定义」（契约：窗口即卡片；padding 上/左 0、右/下 1px 换取 0.5px 边框不被 per-pixel alpha 裁掉，即原 fix6 的结论；html/body/#root 背景必须 transparent 保逐像素穿透；圆角随 `--radius-window` 内缩 2px），再删掉下游全部死声明。权威定义故意不带 `!important`，让文件尾的 `prefers-reduced-transparency` 覆盖层重新赢过基础层——这顺带修好一处既有偏差：Cathedral 层与 Unified 层的 `background` 声明排在「降低透明度」覆盖之后，把它压死了，导致该辅助设置下窗口仍是半透明；现在恢复设计意图的不透明 `#f5f5f7` / `#1c1c1e`（见 README「待真机验证」新增条）。用户此前在工作树里试改未生效的两行（padding 20px、border 2px）随本次一并吸收：按级联终值还原，除上述辅助设置修复外渲染结果与收敛前逐像素一致，但「间距/线宽/圆角」从此只改头部一处。`styles.css` 3942 → 3705 行（+52/-289），测试例数不变（73 例），`tsc --noEmit` 与 `cargo check --all-targets` 仍零报错零警告；亮暗两主题下的实际渲染需真机复核。

- **列表首尾卡片被渐隐遮罩盖住（2026-09-05）**：呼出面板后按下键把列表滚走，再按上键回到第一项，首项顶部会被列表顶部的渐隐遮罩压住一道阴影，继续按上键也不再复位。根因由 Playwright 量出：`.history-list` 用 `padding: 12px 0` 加首项 `margin-top: 2px` 预留 14px，正是为了躲开 `mask-image` 的 10px 渐隐（`styles.css` 里这条意图本来有注释），但「保持选中项可见」用的是 `scrollIntoView({block:'nearest'})`，它只认滚动口的原始边缘，会把这 14px 当成多余空间滚掉——回到首项时 `scrollTop` 停在 14、顶边空隙从 14px 变 0px；底边同病，选中末项时底边空隙从 12px 变 0px。修法是把「什么算可视区」交回 CSS：`scroll-padding-top: 14px` / `scroll-padding-bottom: 12px` 与预留留白同源，`nearest` 从此不再抹平它，判定与效果各归其位，`App.tsx` 一行未改。上一提交新增的 `navigation-visual-regression.spec.js` 之所以漏过，是它的 `visible` 写作 `selectedRect.top >= listRect.top - 1`，把「贴到滚动口边缘」当成可见，而这恰恰就是症状；现按渐隐宽度收紧，实测把 `scroll-padding` 撤掉即变红。测试：新增 `tests/panel-harness.js`（三条浏览器用例共用的 mock bridge 与 `FADE_INSET`）与 `tests/first-item-top-clip.spec.js` 2 例，`test:browser` 1 → 3 例，纯模块 73 例不变；`styles.css` +6 行、`panel-harness.js` +71、`first-item-top-clip.spec.js` +74、`navigation-visual-regression.spec.js` +9/-62。未改变 IPC、模式状态机或粘贴链路。
