# 剪贴板工具如何「监听复制动作」—— 实现调研

> 调研时间：2026-09-10
> 配套文档：《剪贴板工具-呼出到自动粘贴流程实现调研.md》（本文是其「阶段 0」的深挖）
> 目标：把"用户按下 Ctrl+C / 点了复制"这件事，从系统层面如何被感知、如何读取、如何过滤，讲透并落到可实现的代码

---

## 0. 先纠正一个关键认知：系统没有"复制事件"

Windows **不提供**"用户执行了复制"的通知。它提供的只有一件事：

> **剪贴板的内容变了。**

所以所有剪贴板工具做的事都是同一个逻辑：

```
监听"剪贴板变了" → 立刻读取 → 反推/过滤出"这是一次值得收录的复制"
```

这个前提决定了后面所有设计：**为什么需要去重、为什么需要来源过滤、为什么用键盘钩子做判断是不可靠的。**

---

## 1. 三条 Win32 途径：只有一条能用

微软官方文档明确列了三种监视剪贴板的方式，并直接给出了取舍结论：

| 方式 | API | 通知机制 | 官方评价 |
|---|---|---|---|
| **轮询序列号** | `GetClipboardSequenceNumber()` | 定时器比对序列号 | **不要用**。浪费资源，且可能漏掉更新 |
| **剪贴板查看器链** | `SetClipboardViewer()` | `WM_DRAWCLIPBOARD` / `WM_CHANGECBCHAIN` | 只为向后兼容保留。**链中任何一个应用有缺陷就会弄坏整条链** |
| **剪贴板格式侦听器** | `AddClipboardFormatListener()` | `WM_CLIPBOARDUPDATE` | **推荐，新程序的唯一正确选择** |

### 三者的实际差异

**① 查看器链为什么脆**
每个查看器窗口收到 `WM_DRAWCLIPBOARD` 后必须**手动转发给链上的下一个窗口**，退出时必须调 `ChangeClipboardChain` 摘除自己，系统再广播 `WM_CHANGECBCHAIN` 通知其他人转接指针。任何一个环节没做好，链就断了 —— 链断了之后，排在后面的所有监听者**永久收不到通知**，而且没有任何报错。

Ditto 就是在这个机制上做了大量容错：定时器周期性检查连接是否还在、用自定义消息 `WM_CV_IS_CONNECTED` 做 ping 校验、发现掉线自动重连。这套补偿逻辑本身就是"这条路的代价"。

**② 格式侦听器为什么是对的**

```cpp
// 创建窗口时注册
AddClipboardFormatListener(hwnd);

// 销毁窗口时对称注销（句柄可能被重建，务必配对）
RemoveClipboardFormatListener(hwnd);

// 窗口过程中收通知
case WM_CLIPBOARDUPDATE:
    // 剪贴板内容变了，在这里读取
    break;
```

系统维护监听者列表，谁复制都会广播到你，不需要维护链、不需要转发、不需要容错。C# 里也是同一套：

```csharp
[DllImport("user32.dll", SetLastError = true)] static extern bool AddClipboardFormatListener(IntPtr hwnd);
[DllImport("user32.dll", SetLastError = true)] static extern bool RemoveClipboardFormatListener(IntPtr hwnd);
const int WM_CLIPBOARDUPDATE = 0x031D;

protected override void OnHandleCreated(EventArgs e)   { base.OnHandleCreated(e);   AddClipboardFormatListener(Handle); }
protected override void OnHandleDestroyed(EventArgs e) { RemoveClipboardFormatListener(Handle); base.OnHandleDestroyed(e); }

protected override void WndProc(ref Message m)
{
    if (m.Msg == WM_CLIPBOARDUPDATE) { /* 读取剪贴板 */ }
    base.WndProc(ref m);
}
```

**③ 序列号不是完全没用**
`GetClipboardSequenceNumber()` 每次剪贴板变化自增，它不适合做**主要**检测手段，但很适合做两件事：
- 与内容比对配合，判断"内容虽然一样，但确实又复制了一次"（见 7.3 的轮询缺陷）；
- 读取失败重试时，确认内容已经稳定下来。

**④ 顺带排除一个常见误解**
`WM_COPY` / `WM_CUT` / `WM_PASTE` 这三个消息**只对本进程内的 Edit / ComboBox 控件有效**，是控件级别的通知。子类化自己的控件能抓到自己的复制，但**完全无法监听其他应用**的复制动作。它不是全局监听方案。

## 2. 读取为什么要重试：`OpenClipboard` 竞态

**同一时间只有一个窗口能打开剪贴板。** 剪贴板被占用时，`OpenClipboard()` 直接失败。

而 `WM_CLIPBOARDUPDATE` 到达的那一刻，往往正是：

- 复制源应用**还在往剪贴板里写**（它刚发完通知，可能还有别的格式没写完）；
- 另一个剪贴板工具也收到了通知，**正在读**；
- 某些系统组件在操作剪贴板。

所以"通知刚到就读取失败"是**日常事件，不是异常**。必须做成：

```
收到 WM_CLIPBOARDUPDATE
  → 尝试 OpenClipboard
  → 失败：等 20~50ms，重试，最多 N 次（常见 5~10 次）
  → 仍失败：放弃这一次，但不能死等（剪贴板被恶意/异常进程长期占用时不能把 UI 拖死）
```

两个容易踩的点：

1. **读取侧没有现成的重试封装**。.NET 的 `Clipboard.SetDataObject(data, copy, retryTimes, retryDelay)` 有重试参数，但那是**写入侧**；读取侧的 `GetDataObject()` 没有等价重载，得自己写"捕获异常 → 等待 → 重试"循环（WinForms 抛 `ExternalException`，WPF 抛 `COMException`）。
2. **读取必须放到独立线程**。Ditto 专门开了 `CCopyThread` 做这件事，原因有两个：一是读大对象（比如一张大位图）会阻塞主线程导致托盘/弹窗卡顿；二是连续快速复制时，主线程来不及处理会**丢数据**。

## 3. 延迟渲染：监听方最容易漏数据的地方

这是理解"为什么关掉 Excel 之后刚才复制的表格就粘不上了"的钥匙，也是很多剪贴板工具数据不全的根因。

**机制**：复制方调用 `SetClipboardData(format, NULL)`（`hData` 传 NULL）时，并不是真的把数据放上去了，而是放了一个**"你要的时候我再生成"的承诺**。之后：

- 有人请求某个未渲染的格式 → 系统给剪贴板所有者发 **`WM_RENDERFORMAT`** → 所有者此时才 `SetClipboardData` 真正放数据；
- 所有者即将退出、还有未渲染的格式 → 系统发 **`WM_RENDERALLFORMATS`** → 所有者必须在销毁前把所有格式物化（OLE 场景对应 `OleFlushClipboard()`）；
- 如果所有权被清空 → 所有者收 `WM_DESTROYCLIPBOARD`，用来释放私有格式占用的资源。

**对监听方的三个实际影响**：

1. **通知到达时，某些格式可能取不到有效载荷**。你枚举 `EnumClipboardFormats()` 看得到格式，但 `GetClipboardData()` 拿到的可能是空句柄 —— 因为还没渲染。
2. **你主动请求重格式，可能让源应用卡一下**。渲染请求是在消息处理中**同步执行**的，生成耗时数据（大图、复杂 HTML）会冻结所有者的 UI。所以监听方最忌讳"把所有格式全拉一遍存起来"。
3. **所有者进程退出前没物化，你之前读到的东西就是最后的了**（关源应用后失效）。

**实践策略**：优先只取轻量格式（`CF_UNICODETEXT` 为主），对重量格式做按需或降级处理，读取失败时不要把整次复制丢掉。这也是为什么 Ditto 用"分格式 Aggregator + 独立读写线程"的架构 —— 它要处理的就是这里的各种畸形情况。

## 4. 反推与过滤：从"剪贴板变了"到"这是一次复制"

拿到通知、读到内容之后，还要做三层过滤，否则收录的历史会一团糟。

### 4.1 排除自己写入的（防回环）

剪贴板工具自己写回剪贴板时（用户点选某条要粘贴），会**触发自己的监听器**。不处理就会形成回环：自己写 → 收到通知 → 又收录一条 → 列表里堆满重复项。

标准做法：

```cpp
HWND owner = GetClipboardOwner();                 // 谁最后把数据放上去的
if (owner) {
    DWORD pid = 0;
    GetWindowThreadProcessId(owner, &pid);
    if (pid == GetCurrentProcessId()) return;     // 是我自己，忽略
}
```

或者简单粗暴：写剪贴板前设一个 `ignoreNextNotification` 标志 / 短时间窗，下次通知直接丢弃。

> 注意 `GetClipboardOwner()` 可能返回 `NULL`：此时剪贴板**没有被任何窗口拥有**（通常是所有者已退出，或剪贴板被清空）。这是正常状态，不是错误 —— 剪贴板没主了内容依然可能在。

### 4.2 识别来源应用

这是 ClipboardFusion 的「按应用规则」、CopyQ 的「忽略从指定窗口复制的内容」、以及各类"密码管理器不入历史"功能的底层能力。

```cpp
HWND owner = GetClipboardOwner();
DWORD pid = 0;
GetWindowThreadProcessId(owner, &pid);
// → Process.GetProcessById(pid).ProcessName / .MainModule.FileName
```

**局限（必须知道）**：

- `owner == NULL` 时拿不到来源；
- 拿到的是"**最后把数据放上剪贴板的窗口**"，这不总是等于"用户在那一瞬间的前台程序"（后台程序也可能写剪贴板，比如下载工具、同步工具）；
- **位数限制**：要完整读取 64 位进程的信息，你的进程也必须是 64 位（32 位进程读 64 位进程的 `MainModule` 会受限）；
- **备用启发式**：在收到通知的瞬间取 `GetForegroundWindow()`，多数情况下更接近用户的直觉。实践里两者可以结合：先取 owner，owner 为空或明显不合理时退回前台窗口。

### 4.3 不要用键盘钩子来判断"发生了复制"

用 `WH_KEYBOARD_LL` 抓 `Ctrl+C` 看起来很直接，但**不该作为主方案**，因为"复制"的来源远不止 Ctrl+C：

- 右键菜单 → 复制
- 编辑菜单 / 工具栏按钮
- `Ctrl+Insert`（终端、Unix 风格应用）、`Shift+Insert`
- 浏览器、Excel 里的复制按钮
- 拖放（D&D，走 COM `IDataObject`，**根本不经过键盘**）
- 条形码扫描枪、自动化脚本、其他程序内部直接调 `SetClipboardData`
- 甚至粘贴后源程序自己回写剪贴板

**真正的权威信号永远是剪贴板本身。** 键盘钩子只能作为补充信号，用来回答"这次变化是不是用户主动发起的"这类附加问题，而且它对管理员权限窗口的捕获同样受完整性级别限制（见配套文档的 UIPI 部分）。

### 4.4 内容级过滤

- **按格式**：只收录关心的格式（纯文本 / 图片 / 文件列表），忽略内部私有格式；
- **按内容**：长度阈值、敏感前缀（如信用卡号模式）、连续空白；
- **按来源 URL**：浏览器复制的 `HTML Format` 里通常带 `SourceURL` 字段（不过从输入框之类用户内容复制时经常省略），可以用来给条目附上来源，或据此过滤。

## 5. 一个很实用但少有人提的机制：三个"隐私标记格式"

Windows 的剪贴板历史和云同步（Win+V / 跨设备）默认会收录**所有**应用放上去的内容。为了让密码这类秘密不被记录，源应用可以额外放几个**已注册格式**作为标记：

| 注册格式名 | 效果 |
|---|---|
| `ExcludeClipboardContentFromMonitorProcessing` | 本次复制**既不进历史也不进云同步**（最强） |
| `CanIncludeInClipboardHistory`（DWORD 值 0） | 只压制**剪贴板历史** |
| `CanUploadToCloudClipboard`（DWORD 值 0） | 只压制**跨设备同步** |

**这正是密码管理器复制的密码不会出现在 Win+V 里的原因。**

对剪贴板工具来说，这个机制有三层价值：

1. **尊重源应用的隐私意愿**：监听时先检查这些标记格式，命中就**不要收录**。这是一个负责任的剪贴板工具应有的行为，也是 Trim 掉"用户用密码管理器复制密码 → 被你的工具默默存进 SQLite"这类事故的关键；
2. **可检测性**：通过 `RegisterClipboardFormat("ExcludeClipboardContentFromMonitorProcessing")` 拿到格式 ID，再用 `IsClipboardFormatAvailable()` 判断本次复制是否带了这个标记。名字一样返回同一个 ID，跨应用可以共享这个约定；
3. **自己写回时也可以考虑加标记**：如果工具要往剪贴板写敏感内容，同样可以带上这些格式。

## 6. 另一条路：WinRT 剪贴板历史 API

如果目标不是"实时监听每一次复制"，而是"**读取系统已经存好的历史**"，Windows 10 1809 起提供了官方 API：

| API | 用途 |
|---|---|
| `Clipboard.ContentChanged` | 剪贴板内容变化事件 |
| `Clipboard.HistoryChanged` | **剪贴板历史新增条目事件** |
| `Clipboard.GetHistoryItemsAsync()` | 取历史列表，每项有 `Id` / `Content`(DataPackageView) / `Timestamp` |
| `Clipboard.IsHistoryEnabled()` / `HistoryEnabledChanged` | 历史是否开启 |
| `Clipboard.IsRoamingEnabled()` / `RoamingEnabledChanged` | 云同步是否开启 |
| `Clipboard.SetHistoryItemAsContent(item)` | 把某条历史恢复为当前剪贴板内容 |
| `Clipboard.DeleteItemFromHistory(item)` / `ClearHistory()` | 删除 / 清空 |

C# 示例：

```csharp
var result = await Clipboard.GetHistoryItemsAsync();
if (result.Status == ClipboardHistoryItemsResultStatus.Success) {
    foreach (var item in result.Items) {
        var view = item.Content;
        if (view.Contains(StandardDataFormats.Text))
            Console.WriteLine($"{item.Id}: {await view.GetTextAsync()}");
    }
}
```

**门槛与致命限制**：

- 需要 **Windows 10 1809（17763）及以上**；
- **`GetHistoryItemsAsync()` 只能在应用处于前台时调用，否则返回 `AccessDenied`** —— 对一个常驻后台、靠热键呼出的剪贴板工具来说，这是硬伤；
- C++/WinRT、C#、PowerShell 都能直接调；Electron/Node 需要走 `edge-js` 之类的互操作，或者编一个独立的 helper 进程。

**结论**：适合做"导入系统历史""清空系统历史"这类功能，**不适合当实时监听的主力**。

## 7. 各运行时实际怎么做

### 7.1 原生 Windows（C++ / C#）—— 完整推荐链路

```
AddClipboardFormatListener
  → WM_CLIPBOARDUPDATE
  → 独立线程 + 带重试读取（20~50ms × N 次）
  → 过滤：GetClipboardOwner 排除自身 / 按进程名排除（密码管理器等）
        + 检查 ExcludeClipboardContentFromMonitorProcessing 等隐私标记
  → 多格式提取（文本 / HTML / 图片 / 文件列表）
  → 去重（与上一条比对）+ 条数上限
  → 落库（SQLite）
```

### 7.2 Electron / Node —— **没有剪贴板变化事件**

这是做桌面剪贴板应用最先撞上的墙：**Electron 的 `clipboard` 模块从来没有提供 change 事件**（社区长期 issue `electron/electron#2280` 至今没有原生事件）。而且近版本虽然把 API 现代化了（Promise 化的 `clipboard.read()` / `write()` + `ClipboardItem` 多格式），**依然没有事件**。

三条可行路径：

**① 定时轮询（最简单，个人工具够用）**

```js
let last = clipboard.readText();
setInterval(() => {
  const now = clipboard.readText();
  if (now !== last) { last = now; onClipboardChanged(now); }
}, 500);
```

- 间隔 **500~1000ms** 起步，CPU 占用几乎可忽略；不要低于 250ms；
- **缺陷**：内容相同时检测不到 —— 用户连续复制两段一模一样的文本，第二次不会触发。而且 Electron 没有暴露 `GetClipboardSequenceNumber`，你**没法**用序列号补救，只能靠内容比对；
- 启动时要做首次初始化，否则第一次会误判为"变化"。

**② 用现成的"非轮询"包**

`clipboard-event` / `node-clipboard-event`（同一套东西）提供了 `change` 事件：

```js
const clipboardListener = require('clipboard-event');
clipboardListener.startListening();
clipboardListener.on('change', () => { /* ... */ });
clipboardListener.stopListening();
```

它的实现方式很关键：**不是原生模块，而是 spawn 一个平台相关的小可执行文件，从 stdout 读通知**。
- Windows 用的是预编译的 `clipboard-event-handler-win32.exe`（一个用 C# 写的 `AddClipboardFormatListener` 小程序，源码就 2KB）；
- macOS 是 swift 编译的、Linux 是 gcc 编译的，**非 Windows 平台需要 `chmod +x`**。

打包注意事项：**这个 exe 必须从 asar 里解包**（`asarUnpack`），否则运行时找不到/不能执行。
维护风险：包最后发版是 2022 年，不算活跃。

**③ 自己写原生模块（最可靠，成本最高）**

用 N-API（node-gyp / node-addon-api）或 Rust 的 napi-rs 实现 `AddClipboardFormatListener` + 回调桥接。优点是真正的系统级事件、零延迟、零轮询；缺点是要处理 Electron 的 ABI 差异和 `electron-rebuild`，跨平台还得各写一套。

**推荐组合**：轮询做基线（简单、够用、零依赖）→ 有性能或精度诉求时上原生模块 / helper 进程。

### 7.3 轮询的正确写法（避开那几个经典 bug）

```js
class ClipboardWatcher {
  constructor({ intervalMs = 500, onText }) { ... }
  start() {
    this.last = clipboard.readText();      // 初始化，避免首帧误判
    this.timer = setInterval(() => this.tick(), this.intervalMs);
  }
  tick() {
    const now = clipboard.readText();
    if (now === this.last) return;         // 相同则跳过
    this.last = now;
    this.onText(now);
  }
}
```

必须额外处理的：

- **连续相同内容检测不到**（上面的核心缺陷，只能接受或改用原生方案）；
- **去重**：不要只跟"上一条"比，建议跟最近 N 条比，避免用户 A→B→A 时存两条 A；
- **空内容**：`readText()` 返回空字符串时不要入库；
- **条数上限与内存**：历史必须封顶（Win+V 自己只留 25 条），否则长期运行会吃内存；
- **暂停/恢复**：工具自己写剪贴板时要暂停监听，否则回环（对应 4.1）。

## 8. 给本项目（Electron + better-sqlite3）的落地建议

```
主进程常驻
  ├─ 监听层：轮询 reader（基线）→ 后续可替换为原生模块
  ├─ 过滤层：自身写入排除 + 进程名黑名单（密码管理器）+ 隐私标记格式检测
  ├─ 清洗层：去重、限流、条数上限、多格式提取
  └─ 存储层：better-sqlite3 落库 → 通知渲染层刷新
```

短中期最务实的选择：**先上 500ms 轮询 + 内容去重 + 条数上限**，把"连续复制相同内容检测不到"作为一个已知限制记录下来；等真需要零延迟/精确事件时，再做一个 N-API 原生模块替换掉监听层，上层接口保持不变。

另外别忘了：**写回剪贴板时要暂停监听**，这个和配套文档里"还焦点 + 自动粘贴"的流程是同一个回环问题的两端。

## 9. 排查清单

1. 用的是 `AddClipboardFormatListener` 而不是查看器链或轮询？（原生侧）
2. `AddClipboardFormatListener` / `RemoveClipboardFormatListener` 是否成对，句柄重建时有没有重注册？
3. 读取有没有做**重试**？失败时有没有超时上限？
4. 读取是否在**独立线程**？
5. 有没有用 `GetClipboardOwner()` + `GetWindowThreadProcessId()` 排除**自己写入**？
6. 有没有按进程名维护**黑名单**（密码管理器、远程桌面、同步工具）？
7. 有没有检查 `ExcludeClipboardContentFromMonitorProcessing` 等**隐私标记格式**？
8. 连续复制相同内容能不能被感知？（用轮询就一定不能，需明确取舍）
9. 是否处理了**延迟渲染**导致的空句柄 / 源应用退出后的失效？
10. 历史有没有**条数上限**？内存会不会无限增长？
11. Electron 侧：`clipboard-event` 用的话，exe 有没有 `asarUnpack`？
12. 工具自己写剪贴板时，监听有没有**暂停**？
