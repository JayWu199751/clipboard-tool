# 剪贴板监听走系统通知，且「读不到」必须显式重试

600ms 定时轮询有两个改不掉的代价：延迟是「复制后 0–600ms 的某个随机点」，以及**一个轮询间隔内的连续复制会丢前一条**——序列号只知道「变了」、不知道变了几次，于是 B 在 t=0、C 在 t=400 复制，t=600 采样只读到 C，B 永远不出现。换成系统通知（`AddClipboardFormatListener`）同时解决这两条：`clipboard_events.rs` 建一个 `HWND_MESSAGE` 消息窗、注册监听、阻塞在 `GetMessageW` 上，收到 `WM_CLIPBOARDUPDATE` 才去读。空闲时 0 唤醒 0 空转。

上事件模型之前先修了一个**必须先修**的东西：读取失败被当成「剪贴板里没有内容」。`clipboard.rs::read()` 原先返回 `Option<Snapshot>`，但 `arboard::Clipboard::new()` 在 3.6 是 `Ok(Self(()))`、永不失败，真正的失败信号（`ClipboardOccupied`）被 `unwrap_or_default()` 吞成空串；空文字在 `poll_baseline` 里不算变化，于是基线被记成空、序列号照旧推进、下一轮序列号短路命中——**这次复制永久消失**。事件模型会让它更致命：通知只发一次，读失败就是彻底错过。所以 `read()` 的契约改成 `ReadOutcome::{Known, Occupied}`——只有「剪贴板被别的程序占着」算不可信（其余错误都是确定的答案：剪贴板里就是没有可读的文字）；不可信的一轮调 `note_untrusted()`，基线不动、序列号不推进、只留下 `pending_retry` 标记。

**「不可信」之后必须有人再叫一次**：纯事件模型下没有「下一轮」可等，系统不会因为我们失败而重发通知。所以每轮返回 false 就用 `SetTimer` 排一次 50ms 后的重试、成功即 `KillTimer`；写盘失败（原有的 `pending_retry` 语义）走同一条路。这是本条里最容易漏的一环。

三个未知项都是真机探针量的、不是推的（读数见 [README](../../README.md)「待真机验证」与 [changelog](../changelog.md)）：提权进程**收得到**通知（UIPI 不拦，这是唯一的门槛）；通知到达时剪贴板**已无人持有**，等到可读文本 0.7ms、截图 13.8ms，都低于两端各自的重试预算，所以**不需要 debounce、不需要放宽重试**；序列号增量恒等于「格式数 + 1」，即**每条通知都对应一次完整复制**、没有半成品。

## Consequences

- **事件源起不来就退回 600ms 轮询**（`main.rs::poll_fallback`）。轮询最坏是慢，事件源最坏是全哑，而全哑只能靠手工 QA 发现。「注册失败即降级」这十几行是刻意买的保险，别当死代码删掉。
- **`read()` 不再有「读失败就下次再说」这条路**。改它的人要同时看 `ReadOutcome` 的两个分支与 `clipboard_events.rs` 的重试定时器：任何一个分支漏了排重试，失败的那次复制就没人再来取。
- 序列号仍然只当短路用（`skip_unchanged`），不承担判定；事件路径下它多了一层用途——挡住「同一内容收到两次通知」，以及让 `pending_retry` 不被短路吃掉。
- 真机未验：低延迟的体感、连续复制的实际表现、4K 全屏截图会不会顶到 80ms 预算（探针只量到普通截图的 13.8ms），以及本应用自己也参与抢锁时读数是否依旧宽松（探针当时是唯一的监听者）。
- `POLL_INTERVAL` 保留，只服务兜底路径。
